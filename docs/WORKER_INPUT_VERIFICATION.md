# Verify large fit inputs inside the actual worker

The item4 provider previously read every preprocessed image/segmentation/property payload through the controller before every fit. It now authenticates the same validated preprocessing receipt, exact 99-case membership and input contract, then checks remote file names/types/sizes before admission. Package and wheel hashes are still checked there. Billing is observed after preflight. Oversized transport arguments refuse before reservation.

The actual provider launch uses one exec under the existing recorded intent, timeout, read-only mounts, blocked network and empty credentials. A stdlib-only guard receives the authenticated complete inventory and hashes every file inside the mounted Volume before importing or executing the reviewed run.py. Missing/extra files, size/hash changes, symlinks and special files refuse. The record is private, exclusive and keyed by the full job binding; a second launch cannot overwrite it. The Volume v2 sync persists it before scientific execution. Different fits can share the private record directory without colliding.

The guard record binds source hash, preprocessing receipt hash, complete inventory hash, file count/bytes and the full job/segment binding. It contains no case identifiers. The original complete inventory remains private. Observation recognizes a proven guard failure as failed execution, not a completed fit. A final fit result cannot be collected without the matching VERIFIED record. Collection retains the verification in the provider receipt. Missing or inconsistent evidence refuses; no resubmission or budget reset is added.

Tests run the actual guard in child processes on synthetic local files, followed by a trivial synthetic program only after verification. The integration test sends the actual provider payload through that guard and back through the real provider status consumer using an SDK-shaped filesystem fixture. It also verifies no preprocessed payload was read by the controller. These are deterministic proofs, not a live Modal/GPU run or scientific approval. Native pinned-client, full server suites and ordinary independent implementation review are still required before deployment.

This removes repeated image payload transfer from the fit preflight; it does not solve the remaining real experiment initialization, package/provider admission, collection-to-scientific-context or final reporting connections. M4 remains incomplete until a new approved experiment passes the full system path.
