# Uninstalled item 6 CPU image preparation draft

This successor of def2 adds a CPU-only purpose to the existing standard pinned image builder and asset lifecycle. It has not built or selected a real image, spent money, made a model/provider call, installed a release, or changed a750. It grants no scientific allowance.

The exact requirements come from the genuine saved, approved item 6 scientific program and package. The unchanged package and approval verifiers run before reservation and again before provider creation. The fixed build lock must include those exact requirements, with exact transitive versions and hashes; it cannot invent or replace them. There is no actual authored contract or item 6 lock yet. If the eventual requirements already match an existing immutable image, the existing default CPU execution path can use it without this optional build.

One fixed operation uses the existing ACTIVE item 6 owner and its original $100 total cap. It never registers or completes an owner. Full image reservations plus prior item 6 assets and compute count; actual workspace billing and full outstanding commitments gate headroom. Item 4's smoke allowance is neither borrowed nor charged. Existing duplicate, uncertainty, HALT and accounting controls remain. A changed source or selection cannot create a second operation. The provider build has fixed CPU/RAM/time limits, no GPU, secrets, mounts or patient inputs; its network-blocked proof sandbox observes the completed image. This reuses the standalone source-only build mechanism, not the paused wheel-volume pipeline.

A new optional root-selected environment mode binds the fixed interpreter `/opt/research-scientific-python/bin/python` to a genuine preserved READY image receipt. Arbitrary interpreter paths, changed requirements, image IDs or proof hashes refuse. The old `/usr/bin/python3` default and native pre-analysis version checks remain. A root selection and an image build receipt are not scientific execution evidence. Actual job proof is still required before analysis imports.

The approval verifier uses a private temporary byte copy of the exact database and any WAL/SHM, checking source file identities, permissions, sidecar presence and hashes before/after. Only the temporary copy can create SQLite SHM; original ledgers and service write permissions are unchanged. Any source drift refuses. This addresses the observed native failure reading a closed WAL database from a read-only namespace without sidecars.
