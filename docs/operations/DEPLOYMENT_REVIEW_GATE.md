# Material deployment review and recovery

A material update to continuing Linux research requires a genuine independent Claude review of its exact source, deployment inputs and settings before affected use. This verifier is a source/configuration boundary, not a new scientific workflow, human grant or unattended-activation decision. Informal discussion and a locally supplied APPROVE string do not satisfy it. Eligible low-impact repairs retain the existing proportional-review policy; that label cannot exempt a changed material release from this gate. Restoring an already reviewed intended mode or exact bytes does not expand the reviewed identity.

The continuing-linux-v1 profile requires the15 fixed configuration, unit and wrapper targets in orchestrator.deployment_review.REQUIRED_TARGETS. It also binds the actual installed launcher aliases and resolved executables, including the protected Codex native binary and its platform package metadata. This is a byte/version dependency check, not an audit of all third-party implementation. No credential or private-key file belongs in the bundle.

## Prepare one immutable review bundle

Use /etc/research-system/deployment-review/bundles/<proposal SHA256>/ with protected root ownership, directory0750 and evidence files0640 for the already trusted administrative group as appropriate. Keep original model/credential access permissions unchanged. The full verifier runs as root in the protected broker; the non-root controller receives only its bounded read-only deployment-status proof. The native Codex executable deliberately remains unreadable to UID997. Do not weaken that boundary for verification.

proposal.json has schema research-deployment-review/v1, profile continuing-linux-v1, exact source and source_root, previous_source and previous_source_root, source archive SHA256, complete source_files inventory, targets and previous_files maps, recovery_sha256, changes, and fixed dependencies. Each target map entry names an absolute path and its sha256/uid/gid/mode. Include every existing target in previous_files; unlisted existing files refuse before an install intent. New targets must be absent. Preserve all previous files as literal originals. recovery_sha256 names a reviewed, human-readable recovery plan that preserves old releases, partial attempts, evidence and active work; it is not permission to reset or fabricate success.

Store the source archive as source.tar.gz and the exact literal files under literals/<SHA256>. All executable/configuration/policy source files, role documents and every generated or previous configuration/unit literal must be present as actual source or private text in the Claude courier prompt. The reviewed proposal binds the complete archive inventory. The verifier parses that prompt and checks the literal bytes, so an input-hash list without the corresponding supplied content cannot count as a review. Snapshot generation remains a preparation operation before review; it does not activate anything.

Preserve the actual courier request.json, response.json, execution.json, protocol.jsonl, intent.json and returned.json without alteration. The accepted result must be APPROVE for the exact source under human-controls or material-deployment. Original stream events must identify claude-fable-5, the tool-free session, one terminal result and the same session/result as response.json. Execution/request/prompt/protocol hashes and the exact courier source are checked. A provider refusal, REQUEST_CHANGES, truncated stream, wrong model or merely recorded human/agent assertion fails closed. Protocol originals are evidence, not cryptographic provider signatures; a malicious root administrator is outside this privilege boundary.

Under changes/<request identity>/ copy the existing original request.json and ordered events. Each proposal changes item has request and applied identifiers. The exact APPLIED event must have been included in the Claude review's recorded-change context. After that real review, record an existing change_requests REVIEW event attributed to agent/family claude/model claude-fable-5/session_id from the original result. Its payload includes the normal applied_event/verdict/rationale/review_evidence fields plus original_review with request_sha256, response_sha256 and protocol_sha256. This links the change outcome to actual provider evidence. Every active application in the same request must be reviewed APPROVE; pending or sticky negative outcomes anywhere in that active set refuse. The selected application must additionally have the exact provider-original link. Superseded selected applications refuse; a new administrative summary cannot replace originals. Freeze this deployment's copied history. Later criticism still reaches the driver via the ordinary change workflow and must block or revalidate affected work as applicable.


For a large history, the ordinary 20 KB context may omit event payloads. The prepared change-bindings.json sidecar and courier --change-bindings option add an explicit bounded selected_applications section while retaining that summary. The gate requires the sidecar itself in the actual delivered private text, its exact source/proposal hash/selection, and exactly one full original selected APPLIED event per proposed request. Each selected event must bind the current source; its actor, payload, identity, request metadata and a valid original chain head at or after that event are checked against the retained chain. A missing, extra, duplicated, altered or stale selection refuses. Complete original small-context reviews remain valid without this optional sidecar. Neither form relaxes the original independent Claude proof or all-active approval and sticky-negative checks.

## Apply and recover without a circular approval

The proposal contains no review, install-receipt or active-pointer hash. Those are created later, so there is no circular configuration/review seal.

1. After actual review and recorded change outcome, call verify_bundle(bundle, source_root, source, installed=False). It reads the actual previous configuration and preserved source, reviewed archive and dependency identities. No mutation or process starts.
2. The reviewed root installer calls begin_install(...) before changing files. It durably records the exact successful pre-install verification. An incompatible original intent is never overwritten.
3. Install only the reviewed bytes under the existing coordinated administrative locks, preserving the original release, original files and partial attempt records. This module does not replace the installer or authorize service/timer activation.
4. Call record_install(...) after the source and configuration files exist with exact ownership/modes. It requires the original matching intent and records actual installed-file readback. An identical completed duplicate returns the original receipt; a partial attempt does not acquire a success receipt merely from an asserted status.
5. The reviewed installer atomically selects active.json containing exactly schema, source, proposal_sha256 and install_receipt_sha256. This pointer selects reviewed installed bytes; it does not itself grant unattended research or enable a service. Keep the original previous selection. Restart the reviewed broker through the existing service manager. Actual process acceptance remains a separate observation.

The root broker calls verify_installed(source_root, source, config_path=actual_config_path, config=loaded_configuration) before admission, model execution, successor registration or scientific dispatch. It must pass its real fixed command-line configuration path, not a value accepted from a request. The verifier loads only the fixed active selection, rechecks original review/installation bindings and current files, and confirms the actual systemd broker MainPID cwd matches the reviewed release. It also checks that the executing verifier module comes from that release. Reading a configured source label alone is insufficient. The result contains running_broker PID/cwd observations; these are fresh readbacks, not immutable receipt fields.

The controller should obtain a fixed no-body deployment_status response from the protected broker before material work and bind that proof to its own source. It cannot manufacture a verdict or select a different review path. Keep status, historical result inspection and deterministic pause/resume independent of this gate, broker availability and scientific evidence. An invalid material bundle must stop affected new work while leaving those controls usable.

Legacy fixture installation/recovery is distinct from continuing-linux-v1 and does not acquire unrelated new target requirements. Current bootstrap, install_release, install_handover_fixture, update_consumed_handover_fixture, install_live_handover and install_drive_connector entry points now refuse before mutation if either fixed live-research controller.json or broker.json already exists, including broken symlinks. The named refusal is EXISTING_LIVE_INSTALLATION_REQUIRES_REVIEWED_DEPLOYMENT; use the reviewed continuing installation/update route. Fresh preparation with neither marker remains available, and importing their read-only helper functions does not trigger the guard. Their original artifacts remain preserved. The new root pre-use boundary detects changed launchers or live source/configuration; it is not a promise that arbitrary root shell operations are constrained by Python code.

Deployment is not yet established by these source changes. Focused tests use explicitly synthetic offline provider fixtures. Actual independent review, installer integration, root-to-controller status proof, running-process identity, recovered original receipts and deployed acceptance are still required before a new material release is used.
